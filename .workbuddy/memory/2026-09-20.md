### ⚠️ 查出的问题（**均未改**）

**① `enemyDmgStr` 只写不读**（`BattleManager.cs:198` 赋值，全项目零读取）
与刚删掉的 `lastDamage*` 完全同类，每轮白算一次 `FormatDamage`。
`playerDmgStr` 是有用的（第 234 行用于「无法破防」日志）。建议删。

**② 减伤没有上限钳制，>100% 时伤害变治疗**（真 bug，低概率）
```csharp
int reduced = amount * (100 - DamageReduction) / 100;   // PlayerData.cs:458
int reduced = amount * (100 - damageReduction) / 100;   // EnemyController.cs:115
// 图鉴 MonsterManualEntryUI.cs:119 / 159 同样写法
```
减伤 110% → 系数 -10% → `reduced` 为负 → `hp -= 负数` → **挨打回血**。
恰好 100% 时是 0 伤害，这是合法的「无敌」设计（技能备忘里就提到用 100% 减伤做僵持），
只有 >100 才坏。建议 `Mathf.Clamp(100 - X, 0, 100)`。

**③ 两个绕过 `RequireOutOfBattle` 的直写口子**
- `ApplyStatBonus` / `ApplyPercentBonus`（`ApplyBlessing` 的两个分支）直接 `attack += ...`。
- 10 个 `Set*` 接口（`SetAttack` 等）只在 `SaveManager` 读档时调用。
目前都只会在战斗外触发（祝福选择 / 读档），**现在没问题**，但是同类风险的开口。

**④ `KabbalahTreeEffect.OnEnterFloor` 会出现部分生效**（低概率）
它做三件事：`SetHP(HP*2)`（不拦）+ `AddAttackCount(1)`（拦）+ `AddDamageReduction(10)`（拦）。
若真在战斗中触发，会「HP 翻倍了但段数/减伤没加」。
现在不可达（进楼层只由移动/传送器触发，都在输入锁之后）。

**⑤ 百分比加成会被整数截断抹掉**
`battleBaseAttack * battlePercentAttack / 100` 是整数运算：基础攻 7、+10% → `70/100 = 0`。
全项目都是 int 运算所以没改，但如果预期「至少加 1 点」，要改用
`Mathf.RoundToInt` / 向上取整。**需用户确认口径。**

**顺带（不是分离问题）**：`PlayerHUD` 显示「魔力输出 = ManaMax」，
而 `BattleUI` 显示「魔力输出 = min(魔力充能, ManaMax)」—— 同一个标签两种含义。

### 商店「逆推」的解释（用户提问）

```csharp
int rawGain  = currentPlayer.Attack * currentNPC.AtkPercent / 100;
int inversed = rawGain * 100 / Mathf.Max(1, currentPlayer.AttackMultiplier);
currentPlayer.AddAttack(inversed);   // 内部又 *= attackMultiplier / 100
```
商店卖的是「**+X% 当前攻击力**」这个绝对值，而 `AddAttack` 的语义是「传进来的值会被系数放大」。
所以先把标称值除掉系数，让 `AddAttack` 内部那次乘法抵消回来 —— 这就是逆推。
**有损**：例 攻击 100、买 +20%、攻击系数 150% → `rawGain=20` → `inversed=13` →
`13×150/100=19`，玩家拿到 19 而非标称 20。干净做法是给商店一个「精确加值」接口（未做）。

### 「系数换算」指的是什么（用户提问）

就是 `AddAttack` / `AddDefense` / `AddHP` / `AddGold` 内部的
`amount * xxxMultiplier / 100`。**只有在对应 Multiplier ≠ 100 时才有取整损失**
（整数截断 = 少给）。按「加成向上取整」应改 `CeilToInt`，但会牵动商店那条逆推
（两边一起改才自洽），所以留作一次性清理。

## 商店逆推 —— 用户的替代提案（00:50，未落地）

用户问：「为什么要逆推的算，直接加 `攻击力 × 购买百分比 × 攻击系数` 不行吗」

**答：可以，而且本质上就是"删掉 `inversed` 那行、直接 `AddAttack(rawGain)`"**
（`AddAttack` 内部那次 `× attackMultiplier / 100` 正好等于 ×攻击系数）。

**核对三条获取路径后发现商店是唯一的异类**：

| 路径 | 是否被系数放大 |
|---|---|
| 属性道具 `StatBoostPickup` → `ApplyStatBoost` → `AddAttack` | ✅ 放大 |
| 祝福 `ApplyStatBonus` | ✅ 放大 |
| 商店 `NPCInteractionUI`（逆推抵消） | ❌ **不放大** |

所以「逆推」不是为了算得准，而是为了**把 `AddAttack` 的系数抵消掉**——
作者自己也这么注释的（`NPCInteractionUI.cs:159`：「正好抵消」）。
它同时引入两次整数截断，最坏情况是**花钱白买**（攻击 10 + 系数 150% 买 +10% → 到手 0）。

**待用户拍板**：改成不做逆推后，商店购买会被系数放大 → 数值平衡变化
（例：攻击 100、系数 150%、买 +10%，从 9 变成 15），可能出现「先堆系数再买属性」的最优解。
若确认要改，三处（HP/攻/防）一起删 `inversed`，并且日志要改成打**实际到手值**
（现在打的是标称 `rawGain`）。另外 `rawGain` 本身也该按取整规则用 `CeilToInt`。

原来 `SimulateBattle` 返回 `int`，用 `-1` 当「无法战胜」的哨兵。

所以改成：

```csharp
public struct BattleSimResult
{
    public bool CanWin;   // 打不出伤害 / 玩家先阵亡 / 到回合上限仍未击败敌人 → false
    public int  HpDelta;  // 正数 = 损失，负数 = 反而回血（不做 0 下限钳制）
}
```

### 与实战对齐的部分

1. **追踪玩家血量**（原来是纯累加损失、不知道玩家死活）→ 现在能判阵亡，
   并因此实现了两条以前模拟不出来的规则：
   - 玩家阵亡 → 立刻收场（不再挨反击）

2. **回合上限**从自带的 `maxTurns = 10000` 改成引用 `BattleManager.MaxTurnCount`（= 200）。
   顺带把 `MaxTurnCount` 从 `private const` 改成 `public const`，避免两处各写一个数字。
3. **去掉 `Mathf.Max(0, totalHPLost)` 钳制** —— 按用户要求，净回血保持负数。
